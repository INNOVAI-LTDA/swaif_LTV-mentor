# Database Architecture: Table Schemas

## deva_accmed_enrollments

```sql
create table public.deva_accmed_enrollments (
  id bigint generated by default as identity not null,
  provider_user_id bigint not null,
  client_user_id bigint not null,
  product_id bigint not null,
  start_day timestamp with time zone null,
  days_left integer null,
  investment real null,
  decision_matrix_status text null,
  status text not null default 'active'::text,
  created_at timestamp with time zone not null default now(),
  updated_at timestamp with time zone not null default now(),
  constraint deva_accmed_enrollments_pkey primary key (id),
  constraint fk_deva_accmed_enrollments_client_user_id foreign KEY (client_user_id) references deva_accmed_users (id) on update RESTRICT on delete RESTRICT,
  constraint fk_deva_accmed_enrollments_product_id foreign KEY (product_id) references deva_accmed_products (id) on update RESTRICT on delete RESTRICT,
  constraint fk_deva_accmed_enrollments_provider_user_id foreign KEY (provider_user_id) references deva_accmed_users (id) on update RESTRICT on delete RESTRICT,
  constraint chk_deva_accmed_enrollments_provider_client_diff check ((provider_user_id <> client_user_id)),
  constraint chk_deva_accmed_enrollments_status_allowed check (
    (
      status = any (
        array[
          'active'::text,
          'finished'::text,
          'suspended'::text,
          'canceled by client'::text,
          'canceled by organization'::text
        ]
      )
    )
  ),
  constraint chk_deva_accmed_enrollments_days_left_non_negative check (
    (
      (days_left is null)
      or (days_left >= 0)
    )
  )
) TABLESPACE pg_default;

create unique INDEX IF not exists uq_deva_accmed_enrollments_triplet_idx on public.deva_accmed_enrollments using btree (provider_user_id, client_user_id, product_id) TABLESPACE pg_default;

create index IF not exists ix_deva_accmed_enrollments_provider_user_id on public.deva_accmed_enrollments using btree (provider_user_id) TABLESPACE pg_default;

create index IF not exists ix_deva_accmed_enrollments_client_user_id on public.deva_accmed_enrollments using btree (client_user_id) TABLESPACE pg_default;

create index IF not exists ix_deva_accmed_enrollments_product_id on public.deva_accmed_enrollments using btree (product_id) TABLESPACE pg_default;
```

# Database Architecture: New Formats and Rules for Metrics

A gramática atual é adequada como formato inicial de configuração humana, mas não está adequada como DSL estável para crescimento multi-cliente sem ambiguidade.

Ela tem pontos fortes em backend/data/metrics.json:
- É legível por operação e por negócio.
- É simples de editar manualmente.
- Já cobre alguns padrões úteis: regra estática por faixa, acumulativa, faixa de pontos e soma livre.

Mas, como gramática de conversão, ela ainda está subespecificada. O principal problema não é sintaxe; é semântica.

**Onde ela está boa**
A estrutura base metrica + score_type + scoring_rules funciona bem para casos simples como:
- Faturamento com faixas mutuamente exclusivas.
- Taxa de Conversão com dois ramos claros.
- Processos com soma por itens selecionados.
- Número de Serviços com multiplicação implícita por quantidade.

Esses casos mostram que a gramática já consegue expressar regras de negócio comuns sem muita verbosidade.

**Onde ela não está boa**
Os problemas mais sérios são estes.

1. A semântica de condition é inconsistente.
Hoje condition às vezes significa:
- comparação numérica, como lt, gte, and
- comparação textual, como eq
- chave descritiva de opção, como description
- multiplicador implícito por item, como nos casos unrestricted_sum

Isso mistura quatro ideias diferentes dentro do mesmo nó.

2. O operador and está sobrecarregado.
Em vez de significar conjunção booleana genérica, ele significa faixa numérica com min e max. Isso é frágil. Se amanhã surgir uma regra do tipo:
- valor > 10 e canal = premium
a sua gramática atual não acomoda isso de forma limpa.

3. O campo description está sendo usado como lógica.
Em casos como Engajamento, Processos e Ferramentas básicas, o description virou seletor funcional. Isso é ruim porque descrição deveria ser texto humano, não identificador semântico. Texto muda. Chave lógica deveria ser estável.

4. O score_type está fazendo trabalho demais.
Hoje score_type define parte da mecânica, mas a própria regra também embute mecânica:
- static usa points
- range usa points_range
- accumulative soma múltiplas regras
- unrestricted_sum multiplica quantidade por points

Isso faz a lógica ficar espalhada entre score_type, condition e formato de points.

5. A normalização está pouco formalizada.
Os campos max_score_basis e mcv resolvem uma necessidade real, mas do jeito atual eles parecem convenção ad hoc, não gramática fechada. O caso mais claro é:
- MAX_VALUE
- MAX_RVALUE
- MAX_OPT
- MCV

Eles existem, mas não definem de forma inequívoca qual é a fórmula de normalização em todos os cenários.

6. Há ambiguidades reais.
Exemplos:
- Em Gratidão, points_range [1, 4] não explica como escolher um valor interno quando o input for compatível.
- Em Engajamento, as subregras somam 20, mas max_score é 10.
- Em unrestricted_sum, não está explícito se o score bruto pode ultrapassar max_score e como isso interage com normalização.
- Não existe semântica formal para no match.
- Não existe semântica formal para prioridade entre regras sobrepostas.

**Minha avaliação objetiva**
Se o objetivo for:
- poucos clientes
- regras simples
- edição manual por time pequeno

a gramática atual serve.

Se o objetivo for:
- novos clientes com regras heterogêneas
- evolução semântica
- validação automática
- engine confiável de conversão

então ela precisa ser estruturada melhor antes de crescer.

**O que eu sugiro ajustar**
Eu sugiro separar a gramática em 4 blocos conceituais.

1. Entrada
Definir explicitamente de que tipo é o valor bruto e qual shape ele tem.

Exemplos:
- number
- string
- boolean
- set de opções
- mapa de contagens

Hoje isso está implícito e a engine precisa adivinhar.

2. Predicado
Trocar o condition atual por uma gramática booleana explícita.

Exemplo conceitual:
- field
- op
- value
- all
- any
- not

Isso evita usar and como operador especial de faixa.

3. Ação de score
Separar o que acontece quando a condição bate:
- assign
- sum
- multiply
- clamp
- range_assign

Hoje isso está parcialmente escondido no score_type.

4. Normalização
Definir a base de normalização como política formal:
- max_score
- rule_max
- configured_reference
- mcv
- no_normalization

Hoje isso está bom como intenção, mas ruim como contrato.

**Uma versão melhor da gramática**
Em vez de manter a estrutura atual como contrato principal, eu migraria para algo desse tipo:

```json
{
  "input": {
    "kind": "number",
    "unit": "R$"
  },
  "scoring": {
    "mode": "first_match",
    "rules": [
      {
        "when": { "op": "lt", "value": 100000 },
        "then": { "assign": 5 }
      },
      {
        "when": {
          "all": [
            { "op": "gte", "value": 100000 },
            { "op": "lte", "value": 500000 }
          ]
        },
        "then": { "assign": 10 }
      },
      {
        "when": { "op": "gt", "value": 500000 },
        "then": { "assign": 20 }
      }
    ]
  },
  "normalization": {
    "basis": "max_score",
    "value": 20
  }
}
```

Isso melhora muito porque:
- condição e ação ficam separadas
- a ordem de execução fica explícita
- a normalização vira contrato
- você consegue evoluir sem quebrar a semântica anterior

**Para acumulativas**
Em vez de depender de description, eu usaria option_key.

```json
{
  "input": {
    "kind": "set"
  },
  "scoring": {
    "mode": "sum_matches",
    "rules": [
      {
        "when": { "contains": "sales_process" },
        "then": { "assign": 5 }
      },
      {
        "when": { "contains": "operations_process" },
        "then": { "assign": 5 }
      },
      {
        "when": { "contains": "hr_process" },
        "then": { "assign": 5 }
      }
    ]
  },
  "normalization": {
    "basis": "max_score",
    "value": 15
  }
}
```

**Para unrestricted_sum**
Aqui a gramática precisa deixar claro que a entrada é quantidade.

```json
{
  "input": {
    "kind": "number"
  },
  "scoring": {
    "mode": "formula",
    "formula": {
      "multiply": [
        { "var": "input" },
        { "const": 2 }
      ]
    }
  },
  "normalization": {
    "basis": "mcv",
    "value": 6
  }
}
```

Se quiser manter sem fórmula genérica, um meio-termo bom seria:

```json
{
  "input": {
    "kind": "number"
  },
  "scoring": {
    "mode": "per_unit",
    "points_per_unit": 2
  },
  "normalization": {
    "basis": "mcv",
    "value": 6
  }
}
```

**Para range**
Hoje é o ponto mais frágil. Eu evitaria points_range como conceito genérico sem política explícita. Melhor seria algo como:
- assign_range_max
- assign_range_min
- assign_input_clamped_to_range
- require_secondary_input

Se não houver essa definição, dois clientes vão interpretar diferente.

**Melhorias mínimas sem redesenhar tudo**
Se você quiser manter compatibilidade com o formato atual, eu faria pelo menos estas mudanças:

1. Substituir description por key estável.
Exemplo:
- key: sales_process
- label: Vendas

2. Trocar and por range.
Exemplo:
- operator: range
- min: 100000
- max: 500000
- inclusive_min: true
- inclusive_max: true

3. Formalizar prioridade.
Exemplo:
- first_match
- max_match
- sum_matches

4. Formalizar no_match.
Exemplo:
- error
- default_score
- zero

5. Formalizar normalização.
Exemplo:
- basis: max_score | mcv | explicit
- value: número opcional

6. Declarar input.kind por métrica.
Exemplo:
- number
- string
- set
- count_map

Essas seis mudanças já melhoram muito a DSL sem obrigar uma revolução.
